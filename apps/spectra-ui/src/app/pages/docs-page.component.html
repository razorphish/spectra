Spectra exposes versioned REST APIs behind a unified gateway. Start here to learn how to obtain credentials, call endpoints with a valid bearer token, and access your organization’s data according to the scopes you were granted.

Typical flow: read this site → open the developer sandbox → create an Integration (machine-to-machine) or, when enabled, a sandbox application (user-delegated OAuth) → obtain an access token → call the API using the same base URL and audience documented for your environment.

Environments and data: the developer sandbox uses synthetic or subset data for safe experimentation. Staging reflects real integration behavior with PII-cleaned datasets; production holds real customer data and requires approved access (see Production Access).

The public integrator catalog is published as OpenAPI 3 JSON at GET /openapi.json on the API gateway, with interactive Swagger UI at GET /docs. Use these for discovery, codegen, and “try it” flows with a token that is valid for that gateway.

  1. Sign in to the sandbox with your Spectra developer account (Auth0).
  2. Create an Integration and note the client_id; store the client_secret securely.
  3. Use Get access token in the dashboard to mint a bearer token, or call POST /oauth/token on the auth service with client_credentials from your own backend in production.

Integrations are server-to-server OAuth2 clients you register in the Spectra developer sandbox. Each integration has a client_id and client_secret used with the client_credentials grant to obtain access tokens for calling Spectra APIs from your backends and automation—without an interactive user login.

Tokens are minted by Spectra's auth service and are separate from end-user sessions (for example Auth0 access tokens used in the sandbox UI). You choose a display name, optional description, and which scopes the client is allowed to request; those scopes limit what the issued token can do at the API edge.

Create and manage integrations from the developer dashboard after you sign in to the sandbox. Legacy sandbox applications (redirect-based OAuth clients) may be shown or hidden by your organization's settings; integrations are the supported path for machine-to-machine API access.

Choosing Integrations vs sandbox applications

  • Integration (recommended for backends): client_credentials — no interactive user; your server calls Spectra with a minted JWT scoped to your org.
  • Sandbox application (when enabled): OAuth2 app with redirect URIs — for user-delegated flows where a person signs in through your product.
  • If “Add an application” is missing, your org has disabled legacy sandbox apps — use integrations only.
} @case ('authorization') {

Spectra uses several distinct credentials; only one applies per request:

  • Portal session (Auth0) — When you use sandbox-ui, the SPA obtains an Auth0 access token to call /v1/platform/sandbox/... portal APIs. That token is not the same as an M2M token for your integration.
  • Integration (M2M) — client_id + client_secret with grant type client_credentials against the token endpoint documented for your deployment. Use the resulting JWT as Authorization: Bearer when calling Spectra product APIs.
  • Sandbox applications — When your org enables them, OAuth2-style apps with redirect URIs are for user-delegated flows (authorization code). Use them when the resource owner is a person signing in through your app—not for unattended server jobs.

Typing a client_secret into the sandbox “mint token” dialog is convenient for development; for production traffic, mint tokens only from your secure servers. Rotate or revoke a leaked secret immediately from the integration detail page.

API responses are scoped to the organization tied to your integration or user token. Pagination, sorting, and field selection follow each operation’s OpenAPI parameters where defined.

} @case ('calling-the-api') {

Send Authorization: Bearer <access_token> on each request unless an operation explicitly documents otherwise. Use the gateway base URL provided for your environment (for local development, the unified edge is often http://127.0.0.1:3000).

If you open Swagger UI in a browser while the API lives on another origin, ensure CORS is configured on the gateway for that origin; otherwise use curl, Postman, or server-side calls.

Include correlation identifiers when you have them (for example X-Request-Id if returned by the gateway) so support can trace a call end-to-end.

Common HTTP errors

  • 401 — Missing or invalid bearer token, or expired session (portal vs M2M: check which credential you sent).
  • 403 — Authenticated but not allowed (scopes, org, or feature flag).
  • 429 — Rate limited; back off and retry per response hints.
  • 503 with auth_unavailable (or similar) — Auth dependency temporarily unavailable; see dedicated API status when published (v1 program requirement — not only corporate marketing status).

Portal vs data API: JSON from /v1/platform/sandbox/... may use different error / message shapes than public product routes; treat them separately in client logging. See docs/sandbox-portal.md in the repository for sandbox portal behavior.
